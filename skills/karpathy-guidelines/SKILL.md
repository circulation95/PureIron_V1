# Karpathy Guidelines

[Andrej Karpathy의 LLM coding pitfalls 관찰](https://x.com/karpathy/status/2015883857489522876)에서 도출한 행동 원칙. 과잉설계, 가정 숨기기, 범위 밖 변경, 모호한 성공 기준 등 흔한 실수를 줄이기 위한 가드레일이다.

**Tradeoff:** 이 원칙은 속도보다 신중함에 가중치를 둔다. 사소한 작업에는 판단에 맡긴다.

## 1. Think Before Coding

**가정하지 마라. 혼란을 숨기지 마라. 트레이드오프를 드러내라.**

구현 전에:

- 가정을 명시한다. 불확실하면 묻는다.
- 해석이 여러 개면 조용히 하나를 고르지 말고 선택지를 드러낸다.
- 더 단순한 접근이 있으면 말한다. 필요하면 사용자 의견에 푸시백한다.
- 이해하지 못한 채로 진행하지 않는다. 막히면 멈추고, 무엇이 모호한지 이름 붙이고, 묻는다.

## 2. Simplicity First

**문제를 푸는 최소 코드. 추측성 코드 금지.**

- 요청 범위 밖의 기능을 만들지 않는다.
- 한 번만 쓰는 추상화를 만들지 않는다.
- 요청되지 않은 "유연성"이나 "설정 가능성"을 추가하지 않는다.
- 발생할 수 없는 시나리오에 대한 에러 처리를 넣지 않는다.
- 200줄로 짠 것이 50줄로 충분하면 다시 쓴다.

스스로 묻기: "시니어 엔지니어가 이걸 보면 과잉설계라고 할까?" 그렇다면 단순화한다.

## 3. Surgical Changes

**필요한 만큼만 만진다. 내가 만든 흔적만 정리한다.**

기존 코드를 편집할 때:

- 인접한 코드, 주석, 포맷을 임의로 "개선"하지 않는다.
- 망가지지 않은 것을 리팩터링하지 않는다.
- 내가 더 좋다고 생각해도 기존 스타일을 따른다.
- 관련 없는 dead code를 발견하면 말만 하고 지우지 않는다.

내 변경이 고아 식별자를 만든 경우:

- 내 변경 때문에 사용되지 않게 된 import / 변수 / 함수만 정리한다.
- 사전부터 있던 dead code는 요청받지 않는 한 지우지 않는다.

테스트: 변경된 모든 줄은 사용자의 요청과 직접 연결되어야 한다.

## 4. Goal-Driven Execution

**성공 기준을 정의하라. 검증될 때까지 루프를 돈다.**

작업을 검증 가능한 목표로 바꾼다:

- "검증을 추가해라" → "잘못된 입력에 대한 테스트를 먼저 쓰고, 통과시켜라"
- "버그를 고쳐라" → "재현 테스트를 먼저 쓰고, 통과시켜라"
- "X를 리팩터링해라" → "리팩터링 전후로 테스트가 통과하는지 확인해라"

다단계 작업에는 짧은 계획을 명시한다:

```
1. [단계] → verify: [검증 방법]
2. [단계] → verify: [검증 방법]
3. [단계] → verify: [검증 방법]
```

강한 성공 기준은 독립적으로 루프를 돌 수 있게 해준다. "동작하게 만들어"같은 약한 기준은 매번 추가 확인을 요구한다.

## Harness step에 적용하기

이 4원칙은 Harness phase step을 설계·작성할 때 항상 적용한다.

- **Think Before Coding** → step에 가정과 모호한 점을 명시한다. 해석이 갈리면 사용자에게 먼저 묻고 step에 결정 사항을 반영한다.
- **Simplicity First** → step은 작고 자기완결적이어야 한다. 한 step에서 한 레이어/모듈만 다룬다. "유연성"을 위한 코드를 step에 끼워 넣지 않는다.
- **Surgical Changes** → step의 "작업" 섹션에는 만질 파일 목록을 명확히 좁힌다. 금지사항 섹션에 "요청 범위 밖의 리팩터링·정리·기능 추가 금지"를 명시한다.
- **Goal-Driven Execution** → AC(Acceptance Criteria)는 반드시 실행 가능한 명령어로 적는다 (`npm run build && npm test`, `pytest`, `python -m mypy src` 등). "동작해야 한다" 같은 추상적 서술 금지.

**이 원칙이 작동하고 있는지 점검:**

- diff에서 불필요한 변경이 줄었는가?
- 과잉설계로 인한 재작성이 줄었는가?
- 실수 후가 아니라 구현 전에 명확화 질문이 나오는가?
